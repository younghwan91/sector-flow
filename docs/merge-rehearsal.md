# 머지 전 조합 리허설

브랜치가 하나씩 초록이어도 합치면 깨질 수 있다. 인용 줄 번호가 밀리고, 변이 앵커가 어긋나고, 같은 줄을 서로 고친다.
`scripts/rehearse_merge.py` 가 대기 브랜치를 머지할 순서대로 임시 클론에 합쳐 전체 관문을 돈다.

```
uv run python scripts/rehearse_merge.py 브랜치1 브랜치2 브랜치3 --base origin/main
```

관문은 CI 와 같은 것(ruff·연구 컴파일·`pytest --cov`·변경 줄 커버리지·변이 주입 전체)에 `TZ=UTC` pytest 를 더한다.
변이 주입은 수십 분이 걸린다. 빠른 점검은 `--skip verify-merge`, 다른 명령은 `--gate 이름=명령`.
검사·변이 프로세스는 하나당 `RLIMIT_DATA` 6GiB 안에서 돈다(`scripts/memcap.py`) — 변이의 폭주가 2026-11-09 호스트를 OOM 으로 몰아 운영 DB 를 죽였다. 프로세스별 상한은 트리를 못 보므로 하네스의 감시자가 트리 합(RssAnon)이 그 두 배를 넘으면 가장 큰 자손을 죽이고 이유를 stderr 에 남긴다(0.5초 표본이라 커널 상한은 아니다). 검사 쪽 `oom_score_adj` 는 500 으로 올려 커널 OOM 이 와도 운영 DB 보다 먼저 죽는다. CI 러너(2코어·8GB)는 `SECTOR_FLOW_MEM_LIMIT_MB=3000`. 상한에 닿은 변이는 잡힘이 아니라 판정 불가다. 값의 근거: 전체 pytest 의 프로세스별 최대 VmData 0.9GB·RSS 0.85GB(그중 큰 값은 상한 시험이 1GiB 까지 일부러 키운 것, 0.25초 표집).
클론 안에서만 돌아 원래 레포·운영 체크아웃·다른 워크트리에 쓰지 않고, `KR_QUANT_DB`·`KR_QUANT_REPORTS` 를 넘기지 않는다.
충돌이나 실패면 임시 폴더를 남기고 그 경로를 적는다.

## Actions 가 멈춘 동안

GitHub Actions 가 결제 정지 등으로 돌지 않으면 PR 의 CI 결과가 나오지 않는다. 그동안의 절차는 이렇다.

1. 머지 대기 브랜치를 순서대로 놓고 리허설을 끝까지 돈다(`--skip` 없이).
2. 결과(관문별 통과·시간, 브랜치 sha)를 PR 본문이나 코멘트에 적는다.
3. **머지 여부는 사용자가 정한다.**

이 절차는 **초록 CI 규칙을 대신하지 않는다.** 머지 규칙은 그대로 `gh pr checks` 가 초록일 때만이다. 리허설 통과는 "합쳤을 때
로컬 관문이 통과했다" 는 기록일 뿐이고, 3.11 판과 깨끗한 러너는 재현하지 않는다. Actions 가 돌아오면 대기 PR 의 CI 를
다시 돌려 초록을 확인한다.

같은 체크아웃에서 `pytest --cov` 를 겹쳐 돌리면 서로의 측정을 지운다 — `tests/conftest.py` 가 둘 다 실패로 끝낸다. 나란히 돌리려면
리허설처럼 폴더를 나눈다.
